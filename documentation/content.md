# Project writing

Use firsthand context to make the project clear, not to transcribe Tyler's personal history. Select what a visitor needs to understand the problem and the work. Private reflections can inform the draft without appearing in it.

Prioritize projects with bare descriptions, unclear motivation, unexplained outputs or missing use/value. Do not give equal attention to already rich entries just to follow the list order. Start from existing public copy and recorded answers before asking a question. Ask one project-specific opening question, then follow up only on gaps.

Each entry should explain the problem, why available options fell short, what Tyler built, how it works, and how he or others use or benefit from it. This is an editorial check, not a mandatory set of repeated headings. Keep the list description concise and avoid starting it with “I”; first-person narration belongs in the detail reader. Keep Tyler's conversational voice and use no em dashes.

Every project-list row has a title, one concise description and image previews. Fold the audience, purpose or actual use into that description when it adds useful context. Add a compact figures/outcomes row only when there is a distinct supported statistic, user benefit, published output or recognition. Use separate values and labels, not a second bold sentence that repeats the description. Projects without a distinct figure or outcome do not need that row. Do not use build time, tool choices, first-integration trivia, jokes or a vague slogan as a substitute for value. Distribution alone is not an impact claim; spell out event names. Keep demo benchmarks, coverage and audience outcomes distinct. Preserve honest failures without turning them into punchlines. Detailed readers can vary with the material rather than forcing unsupported results into every project.

Group outcomes directly beneath the description and above the screenshots in one quiet strip using the existing raised-surface colour. Use consistent 13px type, slightly stronger values and regular labels, with modest padding. Keep the summary and outcomes close; separate the images and the next project more clearly. The strip is passive information, not a button or a set of pills. Avoid oversized figures, stacked display text and vertical mini-scorecard rules. Recognition uses the same scale. Put dataset coverage and feature counts in the description or detailed story rather than presenting them as user impact. Published output counts can stay when they demonstrate the body of work.

Build a narrative rather than a timeline or inventory. Give each entry a central point, connect the problem to the build, and let use or outcomes follow from that work. A paragraph must advance the reader's understanding; remove repeated motivation, feature lists without purpose, and generic closing lessons. Vary the shape to fit the evidence. Humor, emphasis and exclamation marks should sound natural, never meet a quota. Open each project reader with its title and the same concise one-sentence description used on the list. Show meaningful outcomes immediately after that context, before the narrative. Omit the outcome block when there is no supported result. Then keep the problem and build paragraphs together, followed by project images, deeper technical detail, reflections and related tools. Two narrative lead paragraphs are the default; a project can use `readerLeadCount` when an extra paragraph is needed to explain the actual build. Do not insert outcomes between narrative paragraphs.

Seek an honest, relevant quantified measure for each project: user reach, delivered output, before/after task time, frequency/volume, efficiency, or real cost avoided. Establish the figures from evidence or a direct answer. Label personal estimates and demo benchmarks explicitly, with their scope. A generated assessment score, number of controls or amount of sample data does not prove an achieved user outcome. Keep build times as background context, not an outcome or substitute for user value. Revenue is not profit; published prompts are not evidence of adoption.

Tyler explicitly authorized reasonable workflow estimates on November 10, 2026. A modelled estimate may be used when personal timings are missing. Tyler subsequently clarified that “Est.” should not prefix the card figure. Keep the before/after assumptions, task scope and exclusions in the reader and agent documents, and do not describe the estimate as an independently measured result. Do not present the model as a measured average or invent recurring usage. Time reduction is `(before - after) / before`; use “less time” instead of an ambiguous “faster.” A demo export duration can support one step without establishing the manual baseline. Prefer workflow value over arbitrary file-size reduction.

Annualized avoided-subscription comparisons must identify the product, billing term, currency, pre-tax rate, source URL and check date. They describe the avoided subscription, not a cancelled bill, net savings after development costs, or full feature equivalence. Do not annualize per-task savings without a supported usage frequency.

When a project did not launch or is no longer used, explain the practical outcome and transferable lesson where Tyler has supplied it. Do not fill the gap with generic “I learned a lot” language, assumed learnings or invented audience impact.

A useful tool can be superseded by a better workflow. Newsletter Converter and Image Optimizer solved real publishing problems before Codex agents could handle those tasks directly. Present that as progression, not failure or abandonment. This does not establish that the standalone tools integrate with Codex, and the reason must not be assumed for other projects.

`src/projects.js` is the narrative source. After editing, run `npm run project-text` to keep `projects.md`, `llms.txt` and `llms-full.txt` in sync. Keep unconfirmed notes and detailed interview evidence outside `src/` in ignored working material or Tyler's private evidence ledger. The public repository and site must exclude private customer workflows and operating data.

Keep the list focused on what a project does. Negative traction or non-launch detail belongs in the full story, not the card description or a repeated outcomes block. Describe a general tool by its purpose and capability rather than the subject of a single sample output. Fold catalog counts into useful copy when a separate strip would repeat the description, as with AI Worth Trying. API descriptions should name the actual service and data, distinguishing cached API results, downloaded datasets and the app’s own endpoints. Official API availability alone does not establish that an app uses it.

Every result must make sense to a reader arriving with no prior context. Name the action, input/output and relevant purpose, such as turning email newsletters into articles for a WordPress website. Do not shorten labels to vague phrases such as video prep or newsletter conversion just to fit one line. Let complete result statements wrap naturally with their values inline, preserving readability on narrow screens. Summaries lead with what the tool does; expand unexplained data-source abbreviations or keep exact technical details in the story.

Choose screenshots that show distinct parts of a project, rather than near-identical states of the same screen. If an export only adds a result panel, show the editor and the completed result separately. Capture real application states with public or clearly labelled demo inputs, preserve readable detail, and caption what each view demonstrates.
